# 委派策略细节（brownfield）

> 本文是 `modes/brownfield.md` 的**执行细节**，按需 read。
> mode 文档只留判据，这里放具体做法。

---

## 一、先做一步，再决定派不派

```
两分钟内能自己看清的        → 自己做（这同时就是"看证据"的动作）
中间地带                    → 默认自己做第一步；做完性质自然暴露，判定变成已知事实
明显多文件、多阶段、可并行的  → 派
```

**判据不是任务大小，是"我是否已经理解到能验收"。**

先做一步不是浪费时间——它把"该不该派"从需要权衡的判断，变成已知事实。
**这条是治"秘书化"的关键**：不熟的任务若不先做一步，主代理永远没有第一手认知，只能转述。

## 二、并发派，不要造中间层

子任务互相独立时，**你自己一次性并发派出去**。

> **为什么不能起调度代理**：`spawn_teammate` 只允许 Team Lead 调用
> （`agentTeams.spawnTeammate(caller)` 的 caller 必须是 lead）。
> 调度代理拿到 teammate 角色，**它派不出执行者** —— 这条通路是死的。

**派发前先建任务板**，否则拿不到免费的扇出判据：

```
team_task_create(...)          ← 每个子任务一条，写明 write_scopes
team_task_list(ready: true)    ← 返回的就是"现在能并发几路"
```

`ready` 的行数就是并发宽度，不需要自己推导。
**依赖关系用 `blocked_by` 声明，不要用判断。**

## 三、复用还是新建

**默认新建（fresh）。** 只有三条同时满足才复用：

| 条件 | 说明 |
|---|---|
| **任务同质** | 新任务与它上次做的**属于同一类工作**（同类调研 / 同类改造 / 同类审查） |
| **结论要用** | 你需要它记得上次的结论，否则会重复劳动 |
| **状态未过期** | 上次的调研结论、已读过的文件，对新任务仍然有效 |

复用方式：`send_message` 把新任务发给它（空闲子代理会被唤醒续接）。

**不同质就新建。** 复用不同质的任务是负收益——它带着旧上下文看新问题，更容易套错模板。

## 四、工具选择

| 需要 | 用什么 |
|---|---|
| 独立上下文、干净起点（**默认**） | `subagent`（provider `spawn`，可指定 `agentPreset`） |
| 继承主线决策历史 | `subagent_fork`（provider `fork`，不能另选预设） |
| 具名、可复用、能横向沟通的队友 | `spawn_teammate`（**仅 Team Lead 可调**） |

> `spawn` / `fork` 是 **provider 名**，不是工具名。工具名是 `subagent` / `subagent_fork`。
> **调错会失败，失败后最常见的退化动作就是"放弃委派、自己干"** —— 这是角色退化的一条隐藏成因。

### 两个上限：深度 vs 并发

这是两套独立的限制，混起来算会算错：

| 参数 | 管什么 | 默认 | 当前 |
|---|---|---|---|
| `maxDepth` | **绝对深度**：主代理(0) → 子(1) → 孙(2) → 曾孙(3) | 1 | **3** |
| `maxActiveSubagents` | **整棵树的活跃池**：所有在跑的子孙共用一个池 | 8 | **24** |

**关键：`maxActiveSubagents` 不是"每层几个"，是全树共享。** 根代理不占名额。

```
主代理(0，不占名额)
├── A(1) ─┬─ A1(2) ── A1a(3)     ← 这些全从同一个 24 的池里取
│         └─ A2(2)
├── B(1) ── B1(2)
└── C(1)
```

#### 3/24 的实际容量

| 派法 | 全树占用 | 结果 |
|---|---|---|
| 每层派 1 个（1+1+1） | 3 | ✅ 远低于池 |
| **每层派 2 个（2+4+8）** | **14** | ✅ **推荐，留 10 个余量** |
| 每层派 3 个（3+9+27） | 39 | ❌ 超池 15 个 |
| 只在一层派满 | 24 | ✅ 宽度优先，深度未用 |
| 顶层 4 个 × 各带 5 个 | 24 | ✅ 刚好用满 |

**记住一条：3 层各派 2 个是这套配置的舒适区。** 想派 3 个就得减层或加池。

超限的行为是**直接报错**，不排队：

```
ACTIVATION_LIMIT_REACHED
```

所以深度的实际上限由并发池决定，不是由 `maxDepth` 决定。

#### 三层怎么分工

深度 3 意味着三种角色，别让它们做同一件事：

| 层 | 角色 | 该做什么 |
|---|---|---|
| 主代理(0) | 判断与验收 | 拆解、写任务书、读判决、决定收不收 |
| 子代理(1) | 分块负责人 | 一块活的组织者，可以再拆 |
| 孙代理(2) | 执行者 | 干具体活，通常不再往下派 |
| 曾孙(3) | 例外 | 只在"一个文件里还有多个检查项"这类递归结构才用 |

**默认只用两层。** 三层是给真正嵌套的任务留的，不是用来"多派几层显得专业"。

#### 什么时候真的需要深

深委派只在一种情况下有意义：**任务的子结构是递归的**（比如"审查 100 个文件，每个文件又有多个检查项"）。

如果任务是扁平的（"并行做 12 件独立的事"），**深度 1 就够**，把并发留给宽度。

> 判断方式：你的子任务列表是**一层**还是**嵌套**的？
> 一层 → 调宽度，不调深度。嵌套 → 才需要深度。

#### 池是动态的

- 提高 `maxActiveSubagents`：立即允许更多子代理，已存在的树也受益
- 降低它：**不中断已在跑的**，只是拒绝新的，直到占用降到限值以下
- 子代理结束并清理后才归还名额

所以调大这个值比调大 `maxDepth` 更有用——深度只是"允许"，池才是"能同时干多少"。

#### 改哪里才生效

| 位置 | 优先级 |
|---|---|
| `~/.dsh/profiles/<profile>/cordis.patch.yml` 的 `subagent` 条目 | **高**（覆盖 bundle） |
| 本包 `cordis.patch.yml` 末尾的 `subagent` 条目 | 低（被 profile 覆盖） |

两层都声明同一个 `id: subagent` 时，**profile 生效**。改本包不改 profile 等于没改。

#### 子代理是进程内的

`dsh-subagent-spawn-in-process` 意味着所有子代理跑在**同一个 Node 进程**里，
共享内存与事件循环。24 个并发不是"24 台机器"，而是"一个进程里 24 个任务"。

实际影响：并发太高时，瓶颈通常先出现在 API 速率和内存上，而不是 `maxActiveSubagents` 这个数字。
遇到卡顿先降并发，别急着加池。

### fork 的真实边界

`fork` 只传**对话历史**（切到最后一个 `turn/end`），**不传工具、不传权限、传不了判断力**。
它也不能另选预设——fork 出来的子代理**必然继承父的 persona**。

所以 fork 与 `subagent` 不是两种工作方式，是**同一件事的两种起点**：
一个带着已发生的对话，一个从零。

判据因此不是"要不要继承上下文"，而是一个事实问题：

> 它需不需要知道**已经排除过的方案**、**已经定下的取舍**？

这是事实，不是权衡——主代理当场就知道自己刚否掉过什么。
需要 → `fork`；不需要 → `subagent`（更干净、更省 token）。

### 什么时候该 fork

两种用法，都不需要额外判据：

| 用法 | 形态 | 收尾 |
|---|---|---|
| **同一项目的分支线** | 主线做本体，某条线单独展开（如专利材料、对外文档） | 两种都行，见下 |
| **可分块项目的并发块** | 一块一个 fork，各自推进 | 回流主线 |

**判断"该不该 fork"只有一个问题：这条线做完，主线要不要它？**

- 要 → fork 出来做，按三行证据回流
- 不要（自成一体、做完即完结）→ 仍是 fork，但**不回主线**，做完归档即可

> 第二条容易被忽略：不是所有分支都要汇合。
> 把自成一体的工作硬拉回主线，等于让主线承担它不需要的上下文。

### 两种收尾

| 收尾 | 适用 | 做法 |
|---|---|---|
| **回流** | 结论要被主线使用 | 回三行证据：`改了什么` / `凭什么说对` / `最不确定的一点` |
| **归档** | 自成一体、偏差大、做完即完结 | 不回流，不占主线上下文。主线需要时按路径去读 |

判据：**主线下一步会不会用到它？** 会 → 回流；不会 → 归档。


## 五、可以直接派的活

| 可以派 | 为什么 |
|---|---|
| **基线调研**（`baseline-survey`） | 大量读文件，天然适合独立上下文 |
| 独立模块改造 / 多个独立 bug | 边界清楚、互不干扰 |
| 测试编写、回归验证 | 可独立验收 |
| 按计划逐任务执行 | `subagent-driven-development` |

**自己做**：架构级取舍、跨模块接口变更、风险区改动（`survey/risks.md` 标红的）。

## 六、怎么规划一次委派（3/24 专用）

拿到任务后，按这三步走。**别跳过第一步直接派**——形状判断错了，后面的容量计算全是白算。

### 第一步：判断形状

先看子任务列表长什么样：

| 形状 | 特征 | 怎么派 |
|---|---|---|
| **平铺** | 12 件互不相干的事，每件一步到位 | 只派一层，不派组长 |
| **分块** | 4 块，每块内部还有 3–5 个子项 | 两层：组长 + 执行者 |
| **嵌套** | 每个文件里还有多个检查项 | 三层，但**只在该递归真实存在时** |
| **串行** | B 必须等 A 的结论 | **不派**，或只派 A |

> 判断技巧：把子任务画成缩进列表。**只有一层缩进 = 平铺；两层 = 分块；三层 = 嵌套。**

### 第二步：套容量表

池 24 是**全树共享**的，组长也占名额。下面是 3/24 下能用的形状：

| 形状 | 组长 | 执行者 | 总占用 | 余量 |
|---|---|---|---|---|
| 平铺 8 | 0 | 8 | 8 | 16 |
| 平铺 16 | 0 | 16 | 16 | 8 |
| 平铺 24 | 0 | 24 | 24 | 0 |
| **2 组长 × 各 8 执行** | 2 | 16 | 18 | 6 |
| **3 组长 × 各 6 执行** | 3 | 18 | 21 | 3 |
| 4 组长 × 各 5 执行 | 4 | 20 | 24 | 0 |
| 2+4+12（三层） | 6 | 12 | 18 | 6 |

**推荐区**：平铺 ≤16，或「3 组长 × 各 6」。这两种都留了余量，中间还能临时插一个子代理做补救。

**不要碰**：任何总占用 = 24 的方案。池满了之后，任何一个子代理想再派孙代理都会失败。

### 第三步：超过池怎么办——分波

子任务超过 24 个时，**不要一次全派**。按波次来：

```
总 48 件
  波 1：派 20 个 → 等它们全部结束
  波 2：派 20 个 → 等
  波 3：派 8 个
```

**每波结束，槽位自动归还**，所以总量可以远超 24。

分波的两个注意点：

1. **每波内部要能并行**。如果第 2 波依赖第 1 波的结论，那就不是「分波」，是「串行」，该在主代理这里做汇总再派。
2. **波与波之间要留汇总动作**。20 个子代理各回三行证据，主代理得有时间读。别派完立刻派下一波。

### 形状与派法的对应关系

```
子任务列表
├── 一层 → 平铺派（最多 16 个，留余量）
├── 两层 → 组长 + 执行者（3×6 或 2×8）
├── 三层 → 只在递归结构真实存在时用
└── 超过 24 → 分波，每波 ≤20
```

### 三个常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 平铺任务硬套两层 | 组长没事干，白占名额 | 平铺就平铺派 |
| 派满 24 个不留余量 | 中途想补派一个就失败 | 留 3–6 个余量 |
| 30 个子任务一次派完 | 第 25 个开始报 `ACTIVATION_LIMIT_REACHED` | 分波，每波 ≤20 |

## 七、派发时必做三件事

1. **任务书自包含**：输入路径 / 约束 / 期望格式写清（子代理不继承你的上下文）
2. **指定领域能力**：本子任务要用哪个 skill，在任务书里点名
3. **要求三行证据**：`改了什么` / `凭什么说对（命令与输出）` / `最不确定的一点`

## 八、任务书太多时：让子代理写，自己闭嘴

**问题**：一个任务拆成 80 个子代理，主代理要写 80 份任务书。
每份约 60 行 → 4800 行 ≈ 11 万 token → 128K 窗口直接吃掉 87%。

**解法**：主代理只给「要点」，派子代理把要点展开成任务书并落盘，**子代理闭嘴**。

```
主代理：每个任务写 5 行要点（做什么 / 路径 / 验收命令 / 禁止范围）
   ↓ 并发派撰写者
撰写者子代理：读 templates/brief.md，展开成完整任务书，写进 tasks/<id>/brief.md
   ↓ 回复只有 "✓"
主代理上下文成本：每任务约 3 行（启动 + ✓），而不是 60 行
```

80 个任务：4800 行 → 约 240 行。**降 95%。**

### 三条约束缺一不可（实测结论）

只给「回复只写 done」不够——子代理会用 `send_message` 主动汇报绕过它。三条必须同时给：

```
1. 禁止调用 send_message，禁止任何会通知父代理的工具
2. 最终回复只允许一个字符（如 ✓）
3. 必须给模板路径 templates/brief.md，否则它会自己发明章节结构
```

**实测对照**（同一任务跑三轮）：

| 约束 | 结果 |
|---|---|
| 只说「回复只写 done」 | ❌ 用了 `send_message`，约 40 字进上下文 |
| + 禁止 send_message | ✅ 闭嘴成功 |
| + 给模板路径 | ✅ 六字段结构稳定，与模板完全一致 |

### 撰写者任务书长什么样

```markdown
# 任务：为 tasks/t3 写任务书

## 输入
- 模板：`templates/brief.md`（严格按它的六个字段，不改名、不增删、不调序）
- 要点：修复 parseConfig 空数组崩溃；输入 src/config/parse.ts；
        验收 npx vitest run src/config/parse.test.ts；禁止动 index.ts

## 产出
写到 `tasks/t3/brief.md`

## 硬性约束
1. 禁止调用 send_message，禁止任何通知父代理的工具
2. 最终回复只能是一个字符：✓
```

### 写完要验

撰写者可能漏字段或写错约束。**主代理要跑一遍校验再认**：

```bash
# 检查六个必填字段是否齐全
grep -c "^## 目标\|^## 输入\|^## 领域能力\|^## 约束\|^## 验收条件\|^## 期望产出" tasks/t3/brief.md
# 期望 6；少于 6 就打回重写
```

### 什么时候值得这么做

| 任务书数量 | 做法 |
|---|---|
| ≤5 份 | **主代理直接写**，派撰写者的往返成本高于收益 |
| 6–15 份 | 看单份长度：短则直接写，长（>40 行）则派 |
| **>15 份** | **派撰写者**，分波，每波 ≤20 |

### 先分类，再决定派不派

80 份任务书不是一类东西。先分两堆：

| 类别 | 特征 | 做法 |
|---|---|---|
| **A 类：同构** | 结构相同，只有参数不同（如 20 个文件各跑一次测试） | **参数化生成**，不派撰写者 |
| **B 类：异构** | 每个的约束、验收条件都不同 | **派撰写者**展开 |

**分类判据：把两个任务书并排放，除了路径/名字，还有多少行不同？**
- 只差 1–2 处 → A 类
- 差一半以上 → B 类

### A 类：参数化生成

20 个同构任务，不要派 20 个撰写者。写一份模板 + 一张参数表，一次生成：

```markdown
<!-- templates/param-brief.md 用 {{}} 占位 -->
# 任务：给 {{module}} 补单元测试

## 输入
- 路径：{{src}}
- 现状：{{module}} 已有实现，缺测试

## 约束
- 可写：{{test_file}}
- 禁止：{{src}}（实现不许动）

## 验收条件
```
npx vitest run {{test_file}}
```
```

```
参数表（每行一个任务）：
module         | src                        | test_file
parseConfig    | src/config/parse.ts        | src/config/parse.test.ts
mergeConfig    | src/config/merge.ts        | src/config/merge.test.ts
...
```

**生成方式**：主代理写一个 10 行脚本批量替换，或派**一个**子代理生成全部（不是 20 个）。

**A 类的成本**：主代理写模板（约 30 行）+ 参数表（每行 1 行），**远低于写 20 份完整任务书**。

### B 类：派撰写者，且复用

### 撰写者要复用，别一份一个

**实测确认**：子代理可以复用——`Sending to a resident child reuses its slot`，
本地子代理 `accept later messages and can cold-resume`。

一份一个新撰写者 = **80 次冷启动，模板被读 80 遍**。

正确做法：**一个撰写者连续写 8–10 份，然后换新的。**

```
撰写者 A：写 t1..t8
撰写者 B：写 t9..t16
...
80 份 ÷ 8 = 10 个撰写者
```

**为什么不是 1 个写 80 份**：它的上下文会累积 80 份任务书，
到第 80 份时窗口里躺着前 79 份——等于把问题从主代理搬到了撰写者身上。

**为什么是 8–10 份**：8 × 60 行 ≈ 480 行，占窗口 5% 左右，可接受。

| 方案 | 调用次数 | 模板读取次数 | 撰写者上下文 |
|---|---|---|---|
| 每份新派 | 80 | 80 | 每份都干净 |
| **8 份一批** | **10** | **10** | 峰值约 480 行 |
| 1 个写 80 份 | 1 | 1 | 累积 4800 行 ❌ |

**复用的额外好处**：第 2 份起，主代理给的要点可以更短——撰写者已经知道模板、项目路径约定、
什么算可执行的验收条件。

**复用的代价**：常驻撰写者占槽位。10 个常驻 = 10/24，剩 14 个给执行者。

### 审核层不能复用

审核与撰写相反——**审核者必须每份都是新的**。

| 角色 | 复用 | 理由 |
|---|---|---|
| 撰写者 | ✅ 8 份一批 | 任务书之间独立，前几份不影响后一份质量 |
| **审核者** | ❌ **一份一个** | 前几份的结论会成为基准，导致「越审越松」或「越审越严」的漂移 |

审核要的是独立判断，不能受前面审过的内容影响。


### 分波，别一次派 80 个

池只有 24。80 个撰写者要 4 波：

```
波 1：20 个 → 等全部结束
波 2：20 个 → 等
波 3：20 个 → 等
波 4：20 个 → 等
```

每波结束槽位自动归还。但**总时长会显著拉长**——这是省上下文要付的代价。

### 产出长度不固定

实测中，模板要求约 60 行，子代理实际写了 27 行，但**六个字段全部填实、没有空话**。

**不要为了凑行数要求它写长。** 信息量由任务复杂度决定，不由模板行数决定。
校验只看字段是否齐全、内容是否可执行，不看行数。

### 关键任务加审核层

不是所有任务书都值得审。**只给关键任务加**，否则整体会慢 3–10 倍。

| 该审 | 不用审 |
|---|---|
| 跨模块接口变更 | 单文件、单函数的改动 |
| 会改 `risks.md` 标红区域的 | 纯新增文件 |
| 验收条件难以机器判定的 | 验收条件是一条明确的命令 |
| 子代理可能误解约束的 | 约束只有「可写 X」一条 |

### 审核流程

```
协调者（每个任务组一个）
  ├─ 派撰写者 → 写 brief.md → 回 ✓
  ├─ 派审核者（fresh，独立 persona）→ 读 brief.md + 审核规则
  │    ├─ 通过 → 回 ✓
  │    └─ 不通过 → 写 critique.md，回 ✗
  ├─ 收到 ✗ → 派撰写者重写（把 critique.md 一并给它）
  │    └─ 最多 2 轮；第 3 轮还不过 → 上报主代理
  └─ 最终回主代理一行：`tasks/t1 已通过` 或 `tasks/t1 两轮未过，需人工`
```

### 审核者用 subagent，不用 fork

**这是实测结论，不是偏好**：

| | fork | subagent（fresh） |
|---|---|---|
| 是否继承撰写者的思考过程 | ✅ 继承（会被带偏） | ❌ 不继承 |
| 能否换 persona | ❌ **不能**（`inheritsParentContext` 直接抛错） | ✅ 能 |
| 独立视角 | ❌ | ✅ |

审核要「更严格的要求」，那就得给审核者一个**专门的 persona**。
fork 不支持另选预设，这条路走不通。

### 审核者也要闭嘴

审核意见写进 `critique.md`，回给协调者的只有 `✓` 或 `✗`。

否则详细的批判意见会经协调者流回主代理，省上下文的意义就没了。

### 为什么需要协调者这一层

「审核不通过 → 回退重写」是个循环。**循环必须有人在内部管**：

| 谁管循环 | 代价 |
|---|---|
| 主代理管 | 每轮审核结果都进主代理上下文，白省了 |
| 撰写者自己管 | 做不到（子代理不能在同层派子代理） |
| **协调者管** | ✅ 循环在内部完成，主代理只看最终结果 |

这正好用满 `maxDepth: 3`：主代理(0) → 协调者(1) → 撰写者/审核者(2)。

### 池的账

| 方案 | 每组占名额 | 24 池能跑几组 |
|---|---|---|
| 有协调者：协调者+撰写者+审核者 | 3 | 8 组 |
| 无协调者：主代理直接管 | 2 | 12 组（但循环进主代理上下文） |

**只有关键任务才用协调者**，普通任务主代理直接派撰写者。

## 九、横向沟通

同辈之间可以互相发消息（Agent Teams 支持任意成员互发），但**大多数对齐靠共享状态而非消息**：

- 优先：把结论写进文件 / 任务板，让对方自己读
- 其次：直接 `send_message` 给对方
- 不要：让主代理当二传手转述

**只在两种情况下横向沟通**：接口对齐（A 改了签名要通知 B）、口径统一（同一指标两种算法）。
其余一律回主代理，不要私下决定范围变更。

## 十、判决契约：把"做完了"变成可执行断言

三行证据是**给人读的**；`verdict.json` 是**给脚本验的**。可验收的交付要两者都给。

```bash
python checks/verify.py tasks/<id>/verdict.json
```

退出码：`0` 通过 / `1` 不合法或交付物核验失败 / `2` 打回 / `3` 自检未通过。

### 最小可用判决

```json
{
  "pass": true,
  "failed": [],
  "reviewed_at": "2026-11-04T12:00:00Z",
  "artifacts": [{"path": "src/auth.ts", "sha256": "<64位十六进制>"}],
  "scope": {"base": "HEAD", "allow": ["src/", "tasks/"]}
}
```

> `allow` 里别忘了 `verdict.json` 自己所在的目录（例中是 `tasks/`）——
> 它也是新增文件，会被算进改动范围。漏了会报「改动越界」。

### 三件事决定它有没有意义

| 声明 | 不声明会怎样 |
|---|---|
| `artifacts`（交付了哪些文件） | 脚本不知道交付了什么，只报「未核验」 |
| `artifacts[].sha256` | 只验存在与大小，不验内容对不对 |
| `scope`（允许改哪些路径） | 不知道有没有改到不该改的地方 |

**"没声明"等于"没核验"，不等于"通过"。** 摘要末尾会固定列出未核验项，别把 `[PASS]` 读成整体合格。

### 什么时候必须有判决

| 情况 | 要判决吗 |
|---|---|
| 子代理改了文件、要你决定收不收 | **要** |
| 只是调研、结论写进文件 | 不用，三行证据够 |
| 你自己改的 | 建议要，尤其跨模块改动 |

> 判决由**独立于实现者**的人产出（`reviewer` 字段）。自己验自己时，
> `reviewer` 写 `self` —— 脚本不拦，但你该知道这条证据的强度。

### 完整记录不必进上下文

每次运行会落盘到 `.verdict-log/verdict-<时间戳>.json`（判决原文 + 核验结果 + 未核验项）。
主代理只读摘要一行，需要追溯时按路径去取。`--no-log` 可关闭。
