# 模式：存量深化（brownfield）

> **适用**：已有代码/实验/文献基础，要在其上调研、改造、扩展、深化。
> **判据核心**：先摸基线再动手；最小改动；先查调用方；先复现再修；强委派。

## 前提判断

在进入本模式前，先确认：

- 已有可运行的基线（能跑的代码、完整实验设计、成型文献集）
- 你**尚未**完全掌握它的结构

> **第一动作不是改，是调研。** 不读清结构就动手 = 瞎改。

## 核心判据

1. **先摸基线，再动手**
   先用 `baseline-survey` 产出：
   - `survey/structure.md` 项目骨架
   - `survey/baseline.md` 现有能力边界
   - `survey/hotspots.md` 值得深化的点
   - `survey/risks.md` 改动风险区

   主代理只读摘要（≤15 行），细节留文件。

2. **最小改动**
   只改与目标相关的地方。不顺手重构、不调格式、不重命名无关变量。
   每一点无关改动都在扩大风险面。

3. **先查调用方再改签名**
   改函数签名、返回值、数据结构前，先搜谁在用它。
   破坏调用方是最常见的"修好 A 坏了 B"。

4. **先复现再修**
   修 bug 前先写能稳定复现的最小用例，修完用它验证。
   没有复现的修复等于猜。

5. **尊重既有约定**
   项目已有的命名、分层、错误处理方式，跟着走。
   即使你认为别的写法更好，也先保持一致——一致性比局部最优重要。

6. **能跑才算完成**
   改完必须实际执行（原有测试、构建、启动），证据是命令输出。

7. **一次一件事**
   多个不相关的修改分开做、分次验证。

## 失败模式

- 没读结构就改，改完发现还有三处同样的地方没动。
- 顺手重构无关代码，diff 三百行，review 无法判断。
- 改了内部函数签名，没改调用方，运行时才炸。
- 修了表面症状，根本原因还在（没先复现）。
- 引入新的写法，与项目既有风格不一致，维护者困惑。
- 声称"修好了"但没跑原有测试，回归被破坏。

## 委派策略：**强委派**

存量项目通常模块多、边界清楚，**委派收益高**：

| 可以派 | 为什么 |
|---|---|
| **基线调研**（`baseline-survey`） | 需要大量读文件，天然适合独立上下文 |
| 独立模块的改造 | 边界清楚、互不干扰 |
| 多个独立 bug 的排查 | 见 `dispatching-parallel-agents` |
| 测试编写、回归验证 | 可独立验收 |
| 按计划逐任务执行 | `subagent-driven-development` |

**自己做**：架构级取舍、跨模块接口变更、风险区改动（`survey/risks.md` 里标红的）。

### 派发时必须做的三件事

1. **任务书自包含**：子代理不继承你的上下文，输入路径/约束/期望格式都要写清
2. **指定领域 skill**：本子任务需要文献能力就写"用 lit-search-strategy"，需要绘图就写"用 sci-figure-kit"
3. **要求三行证据**：`改了什么` / `凭什么说对（命令与输出）` / `最不确定的一点`

### 子代理的预设选择

- 需要**独立上下文 + 干净起点** → `spawn`（可指定 `agentPreset`）
- 需要**继承主线决策** → `fork`（继承父预修订，不能另选预设）
- 多个互不依赖的活 → 同一批并发派

## 完成标准

- [ ] 原有测试/构建仍然通过（有输出为证）
- [ ] diff 只包含目标相关的改动
- [ ] 调用方已同步更新
- [ ] 风险区未被动到（或已明确评估）
- [ ] 调研产物已落盘，主代理只留摘要
