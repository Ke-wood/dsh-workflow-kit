# 模式：存量深化（brownfield）

> **适用**：已有代码/实验/文献基础，要在其上调研、改造、扩展、深化。
> **判据核心**：先摸基线再动手；最小改动；先查调用方；先复现再修；强委派。

## 前提判断

在进入本模式前，先确认：

- 已有可运行的基线（能跑的代码、完整实验设计、成型文献集）
- 你**尚未**完全掌握它的结构

> **第一动作不是改，是调研。** 不读清结构就动手 = 瞎改。

## 核心判据

判据正文**只存一份，在 persona 里**（常驻，每轮都在）。本文不再重复，只补它没展开的部分：

| 判据 | 本文补充的执行细节 |
|---|---|
| 先摸基线，再动手 | 用 `baseline-survey` 产出 `survey/{structure,baseline,hotspots,risks}.md`；主代理只读 ≤15 行摘要 |
| 最小改动 | 不顺手重构、不调格式、不重命名无关变量——每一点无关改动都在扩大风险面 |
| 先查调用方再改签名 | 改签名/返回值/数据结构前先搜谁在用。这是"修好 A 坏了 B"的头号来源 |
| 先复现再修 | 修 bug 前先写能稳定复现的最小用例，修完用它验证。没有复现的修复等于猜 |
| 尊重既有约定 | 命名、分层、错误处理跟着走。一致性比局部最优重要 |
| 能跑才算完成 | 改完必须实际执行（原有测试、构建、启动），证据是命令输出 |
| 一次一件事 | 多个不相关的修改分开做、分次验证 |

> **判据只允许被"证据"替换，不允许被"教训"追加。** 每次想加一条时问：能不能改成可执行检查？
> 不能 → 说明这是暂时的人类判断，该由人持有，不该塞给主代理。

## 失败模式

- 没读结构就改，改完发现还有三处同样的地方没动。
- 顺手重构无关代码，diff 三百行，review 无法判断。
- 改了内部函数签名，没改调用方，运行时才炸。
- 修了表面症状，根本原因还在（没先复现）。
- 引入新的写法，与项目既有风格不一致，维护者困惑。
- 声称"修好了"但没跑原有测试，回归被破坏。

## 委派策略：强委派，但分发权始终在你手里

存量项目模块多、边界清楚，**委派收益高**。

### 三条默认动作

```
两分钟内能自己看清的        → 自己做（这同时就是"看证据"的动作）
中间地带                    → 默认自己做第一步；做完性质自然暴露，判定变成已知事实
明显多文件、多阶段、可并行的  → 派
```

**判据不是任务大小，是"我是否已经理解到能验收"。**

### 三条硬规则

1. **探索可以委派，交付必须可验收** —— 禁止"我不懂所以我派出去"
2. **并发派，不要造中间层** —— `spawn_teammate` 仅 Team Lead 可调，调度代理派不出执行者，那条路是死的
3. **默认新建子代理** —— 只有"任务同质 + 结论要用 + 状态未过期"三条同时满足才复用

**自己做**：架构级取舍、跨模块接口变更、风险区改动（`survey/risks.md` 标红的）。

> 工具选择、fork 边界、复用判据、可派清单、横向沟通见 `modes/brownfield-delegation.md`。

## 完成标准

- [ ] 原有测试/构建仍然通过（有输出为证）
- [ ] diff 只包含目标相关的改动
- [ ] 调用方已同步更新
- [ ] 风险区未被动到（或已明确评估）
- [ ] 调研产物已落盘，主代理只留摘要
