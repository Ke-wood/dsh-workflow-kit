# 基线调研（Baseline Survey）

> 适用前提：项目**已有基础**（能跑的代码、完整的实验设计、成型的文献集）。
> 不是从零搭建 —— 所以重点是**摸清现状 + 找深化点 + 识别风险**，不是教人怎么起步。

## 为什么需要这一层

主代理如果不了解基线就派活，等于**瞎改**。但把项目全貌读进主代理上下文又会污染它。
解法：**调研产出到文件，主代理只读摘要 + 关键点**。

## 四份产出（写到 `survey/`）

### 1. `survey/structure.md` — 项目骨架

```markdown
# 项目骨架

## 入口
- 主入口：<路径> — <做什么>
- 关键脚本：<路径列表>

## 目录职责
| 目录 | 职责 | 重要度 |
|---|---|---|

## 关键模块
| 模块 | 位置 | 作用 | 依赖 |
|---|---|---|---|

## 外部依赖
- 运行时：
- 数据：
- 服务/API：
```

### 2. `survey/baseline.md` — 现有能力边界

```markdown
# 现有能力

## 已经能做的
- <能力> — 证据：<文件/函数/测试>

## 明确做不到的
- <限制> — 原因：<技术/数据/设计>

## 半成品 / TODO
- <位置> — 现状：
```

### 3. `survey/hotspots.md` — 深化热点（**最重要**）

```markdown
# 深化热点

## 热点 1：<名称>
- **位置**：
- **为什么值得深入**：
- **预期收益**：
- **预估工作量**：小 / 中 / 大
- **依赖**：<前置条件>

## 热点 2：...
```

排序原则：**收益/工作量比从高到低**。不要罗列所有可能，只留真正值得做的 3-5 个。

### 4. `survey/risks.md` — 改动风险区

```markdown
# 风险区

## 高风险（改了容易坏）
| 位置 | 为什么危险 | 缓解 |
|---|---|---|

## 隐性契约（没写文档但被依赖）
- <位置> — 谁在依赖它：

## 已过期 / 待清理
- <位置> — 说明：
```

## 回主代理的摘要（唯一进对话的部分）

**不超过 15 行**：

```markdown
## 基线摘要

**这是什么**：<一句话>
**现在能做**：<3 条以内>
**主要限制**：<2 条以内>

**建议深化的 3 个点**（按性价比）：
1. <热点> — 收益 <X>，工作量 <Y>
2. ...
3. ...

**必须避开**：<最危险的 1-2 处>

**详情**：survey/{structure,baseline,hotspots,risks}.md
```

## 执行纪律

1. **先读 README / 入口文件**，别急着 grep 全库。
2. **读代码不猜**：结论必须有文件路径支撑。
3. **不评价好坏**，只描述现状 —— 评价是主代理的事。
4. **控制粒度**：结构到"模块"级即可，不要逐函数。
5. **产出即交付**：写完文件才算完成，口头总结不算。
6. **大项目分批**：超过 50 个源文件时，先出目录级，再按热点深入，不要一次全读。

## 反模式

| 错误 | 后果 |
|---|---|
| 把源码大段贴进对话 | 污染上下文，后续每轮重复计费 |
| 只读 README 就下结论 | 与实际不符，误导深化方向 |
| 热点列了 20 个 | 主代理无法决策，等于没调研 |
| 不写风险区 | 深化时踩坑，返工 |
| 结论无文件路径 | 无法验证，等于猜测 |
